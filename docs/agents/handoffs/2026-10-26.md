## Settled Phase 1b decisions

The replacement is a modern Bootstrap panel using versioned REST on ASP.NET Core / .NET 10.
It reaches the C++ business layer over a restricted local named pipe, with no COM dependency
or direct database access. Native commands enforce permissions independently of HTTP handlers.
Keep COM separately for existing desktop tools, database setup, scripts and compatibility.
Do not remove COM registration until those consumers have supported replacements.

Remove PHP completely from administration delivery after replacement parity and migration
acceptance: retire legacy WebAdmin source, packaging, runtime requirements and the old endpoint.
The existing PHP application is still present; #31 did not switch the installer. Do not remove
unrelated machine-wide PHP installations or administrator-managed applications.

IIS can host the ASP.NET Core panel; standalone hosting is also possible. Final production
hosting/service identity, HTTPS provisioning and installer delivery remain unfinished. IIS web
HTTPS and native SMTP/IMAP/POP3 TLS are separate bindings; IIS does not configure mail certificates.

The panel must offer advanced administration, SpamAssassin controls, multiple configurable
DNSBLs and SPF/DKIM/DMARC generation/validation including shared-provider SPF. Remaining work
includes administration parity, full DNS/key lifecycle, SpamAssassin engine packaging and
production hosting/installer/upgrade acceptance. DMARC aggregate reports remain in Phase 6.

Certificate delivery must be user-friendly: guided import (including chain/PFX) or automatic
issuance/renewal, hostname/key/chain validation, listener assignment, expiry/renewal status,
safe activation and rollback. ACME client/provider/challenge/scheduling choices need validation;
automation has not been implemented. Protect keys through narrowly scoped native operations.

## Defender and high-pressure scanning clarification

The maintainer requested optional local Microsoft Defender Antivirus scanning and mitigation,
separate from spam scoring and from Microsoft Defender for Office 365. Source/documentation
review supports feasibility in principle, not confirmed service permissions or capacity.
A dedicated adapter is required: the existing custom scanner's single exit-code mapping is
insufficient for reliable clean/infected/error/unscannable classification.

"Real time" means concurrent receive/send/queue/draft/intermediate activity, not a specified
messages-per-second rate. Cover SMTP receipt/submission, queued delivery, external fetch,
IMAP APPEND/server-saved drafts, imports and changed content. Client-local drafts cannot be
scanned before upload. Gate normal delivery/retrieval on an acceptable verdict for the current
immutable content; changed bytes invalidate it.

Require a durable work queue, bounded workers/resources, fairness, backpressure, crash recovery,
idempotent mitigation and explicit error/hold/retry behavior. Never silently release mail as
clean on scan failure or let scanner remediation corrupt the live store. Prevent internal
duplicate release; remote SMTP acceptance after a lost acknowledgement cannot guarantee
exactly-once delivery. Do not merely increase the existing intended ten-scanner ceiling.

Capacity acceptance includes at least 10,000 queued/in-flight messages, mixed traffic/draft
updates, bursts, outages/restarts and soak. Publish hardware, engine/signature version, message
mix, sustained throughput, queue age/bytes, p95/p99 latency, resource use and recovery behavior.
Set numeric capacity/latency targets from evidence before production approval; retain other
scanner choices if Defender cannot sustain the workload. No benchmark has established this yet.
