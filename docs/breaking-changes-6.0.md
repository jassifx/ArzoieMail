# ArzoieMail 6.0 compatibility and breaking-change register

Approved direction: **2026-10-28 (Asia/Colombo)**. [Frozen scope](version-6-scope.md) owns
the mandatory product outcomes; this register owns operator impact and migration evidence.
Rows describe planned transitions, not completed migrations. Preserve original authorship,
license notices, historical release/schema mappings and mail data. The final release notes
must link each accepted entry and provide tested, version-specific procedures.

| ID | Legacy behavior / new behavior | Affected installations and data risk | Required operator action | Migration / rollback or recovery | Test evidence / status | Release note obligation |
|---|---|---|---|---|---|---|
| BC-001 | PHPWebAdmin replaced by ASP.NET Core administration | Legacy admin URLs, custom PHP pages and role workflows; exposure/lockout risk during cutover | Review parity, credentials/roles, HTTPS URL and custom integrations | Tested installer cutover and disabled old endpoints; backed-up recovery procedure; no active PHP admin fallback in 6.0 | Partial replacement through #42; cutover not implemented | Removed URLs/runtime, replacements and customization conversion |
| BC-002 | VBScript/JScript events replaced by isolated PowerShell | EventHandlers, custom scripts and rule actions; altered side effects can lose/reject/misroute mail | Inventory/convert scripts; review identity, timeout and event semantics | Conversion examples and legacy detection; supported restoration from pre-upgrade backup where feasible, not silent script rewriting | Planned Phase 2; event/argument inventory pending | Every semantic difference, unsupported script and recovery step |
| BC-003 | SQL Server Compact replaced by SQLite | Built-in database users; interruption, conversion or message-store inconsistency | Verified database/mail backup, supported source/version check and migration review | Tested automatic conversion, interruption/retry/recovery and restore; do not promise in-place schema downgrade | Planned Phase 4; normal SQLite plus separate Compact migration lanes required | Source matrix, prerequisites, integrity checks and recovery |
| BC-004 | OS/runtime/toolchain prerequisites modernized | Older Windows and unsupported dependency stacks; failed install/upgrade or unavailable security fixes | Check exact supported OS/edition/security-update arrangement, runtimes and database clients | Prerequisite checks before service interruption; documented supported upgrade/recovery route | Technical minimum exists; production-supported release matrix pending | Distinguish runnable from production-supported; offline prerequisites |
| BC-005 | Protocol/authentication/configuration behavior modernized | Mail clients, relays, DNS/TLS policy and scripts; interoperability, rejection and resync risk | Review each feature/default change and DNS/certificate/client requirements | Version-specific configuration migration, client interop, UID resync and recovery; never reset IDs manually or weaken authentication silently | Planned Phase 3; identifier plan specifies acceptance | Defaults, client impact, authentication/TLS changes and UID resync |
| BC-006 | Non-COM compatibility identifiers retained | Existing installations and upgrade discovery; accidental parallel install or lost paths | Keep executable/service/INI names and installer AppId; distinguish product branding from identifiers | Preserve upgrade detection, paths, schema/backup formats and history; test existing-install upgrade | Retention approved; final upgrade matrix pending | Explicitly list retained names; COM is excluded from retention |
| BC-007 | COM API completely removed; secured management API replaces supported consumers | Administrator, DBSetup/Quick/Updater, data/maintenance tools, regression/volume/VM fixtures, scripts, external integrations, callbacks and COM utilities; loss of management/recovery coverage if removed early | Inventory consumers and API operations/roles; migrate supported automation; replace third-party COM integrations before upgrade | Document secured API credentials/transport and examples; preserve recovery/bootstrap workflows without broad unauthenticated API access; tested restore of a compatible pre-upgrade backup if needed; no COM shim in 6.0 | Decision approved, implementation pending; E10/V6-COM. Existing COM remains in current development code only | Clearly announce removal of ProgID/type library/registration and script/API migration, unsupported integrations and recovery |
| BC-008 | Optional existing open-source webmail introduced | Administrators who opt in; separate session, HTML, attachment, update and credential exposure | Choose supported deployment and configure identity/TLS; PHP allowed only as optional webmail dependency | Independent install/update/uninstall and mail-service continuity; do not remove unrelated PHP applications | Planned Phase 6; application/license/security review pending | Optional dependencies, security boundary, support/update ownership |

For every row, completion evidence must identify implementation PR/revision, affected contracts,
positive/negative migration tests, failure recovery, remaining limitations, operator procedure
and maintainer acceptance. Known unsupported scenarios require an explicit disposition before
release. A successful ordinary regression job is not proof of all upgrade paths.
